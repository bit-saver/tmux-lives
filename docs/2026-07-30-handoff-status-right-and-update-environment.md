# Handoff → tmux-lives: two defects found from the fish-config side

**From:** a session working in `~/.config/fish` on macwork, 2026-07-30. **Not touched by me** — I made no changes to `conf.d/tmux-lives-install.fish`, `~/.config/tmux/tmux-lives.conf`, `functions/tmux-categorize.fish`, `~/.tmux.conf`, or any running tmux server. Diagnosis and evidence only; both fixes belong here because the local copies are vendored and `fisher update` would overwrite them.

Both defects were found incidentally while debugging an unrelated fish-prompt breakage after `brew upgrade`.

---

## Defect 1 — the rendered fragment evicts tmux-continuum's autosave hook (data loss)

**Severity: high.** This silently disables the user's only tmux session-recovery path.

**Root cause.** tmux-continuum implements autosave by injecting `#(.../continuum_save.sh)` into `status-right` and relying on the status bar's periodic refresh to execute it. There is no timer and no daemon — the status-bar interpolation *is* the scheduler. tmux-lives renders `status-right` wholesale, so the injected hook is overwritten and autosave stops permanently and silently.

**Evidence, captured on macwork 2026-07-30 13:2x CDT:**

```
$ tmux show-options -gv status-right
#{T:@tmux_lives_status_right}#(fish --no-config /Users/tyler.hebenstreit/.config/fish/functions/tmux-categorize.fish tick '#538353')

$ tmux show-options -gv status-right | grep -c continuum
0

$ tmux show-options -gv @continuum-save-interval
15
$ date -r "$(tmux show-options -gv @continuum-save-last-timestamp)"
Tue Jul 28 08:56:14 CDT 2026        # ← last successful autosave
$ date
Thu Jul 30 13:23:58 CDT 2026        # ← ~52 hours later, interval is 15 minutes
```

The setting that writes it: `~/.config/tmux/tmux-lives.conf:15`, generated by `__tmux_lives_render_fragment` in `conf.d/tmux-lives-install.fish`.

`@continuum-status` is unset, and no continuum process is running — consistent with the hook never firing rather than firing and failing.

**Impact as observed.** Ten live sessions on this server, four of them running Claude (`Watchface-25`, `Pingy-Android-Part-29`, `Codey-White-Pane-Issue`, `Obsidian`). The resurrect snapshot they would restore from is frozen at Jul 28 08:56. Compounding this, the tmux server (pid 21843, up since Jul 12) is executing a `brew`-deleted 3.6b binary, so it cannot be restarted into its current state — if it dies, recovery falls back to that stale snapshot.

**Proposed fix shape.** Preserve rather than replace. When rendering `status-right`, read the existing value first and re-append any `#(...)` command substitutions the fragment did not author — or, more narrowly and with less coupling, detect tmux-continuum (`@continuum-save-interval` set, or `~/.tmux/plugins/tmux-continuum` present) and append its `continuum_save.sh` interpolation to the rendered string. A documented `@tmux_lives_status_right_extra` passthrough option would let the user re-add it themselves and would also solve the general case for any other status-right-scheduled plugin.

Worth deciding explicitly whether tmux-lives intends to *own* `status-right`. If it does, the plugin should say so in its README and detect continuum specifically, because the failure mode is silent and the cost is data loss.

## Defect 2 — `set -ga update-environment` grows without bound

**Severity: low.** Cosmetic and self-limiting in behavior, but it is unbounded growth and a symptom of a non-idempotent fragment.

**Root cause.** `~/.config/tmux/tmux-lives.conf:69-70` uses `set -ga` (append) rather than `set -g`. The fragment is re-sourced on every tmux config reload, and each reload appends the same two names again. Nothing dedupes.

Generated from `conf.d/tmux-lives-install.fish:187-188`:

```fish
set -a f "set -ga update-environment \"LC_TERMINAL\""
set -a f "set -ga update-environment \"LC_TERMINAL_VERSION\""
```

**Evidence:**

```
$ tmux show-options -gv update-environment | tr ' ' '\n' | sort | uniq -c | sort -rn | head -3
  56 LC_TERMINAL_VERSION
  56 LC_TERMINAL
   1 XAUTHORITY
```

56 copies of each after ~18 days of uptime.

**Proposed fix shape.** Make the append idempotent — read `update-environment`, and append each name only when absent. Alternatively render one `set -g update-environment "<full list>"` with the defaults plus the two additions, which is idempotent by construction but takes ownership of the whole option.

## Related observation, no action requested

`tmux show-environment -g LC_TERMINAL` returns `LC_TERMINAL=ShellFish` as a single server-global value, stamped by whichever client attached most recently. Anything reading it to decide "is the current client ShellFish?" will be wrong whenever a session is attached from a different client than the one that set it.

`functions/tmux-categorize.fish` already does this correctly — `__tcz_client_terminal` (line 113) reads `LC_TERMINAL` from the *client process environ* per client pid, and `__tcz_thp_shellfish` (line 1419) folds that over attached clients. Flagging only so the global value is not mistaken for a usable signal later; the existing per-pid approach is the right one and I am reusing that technique (independently, not by calling into it) on the fish side.
